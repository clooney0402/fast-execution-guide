### 0-3. 공통 UI 원칙

| 원칙 | 정의 |
|------|------|
| **마스킹 일원화** | 개인정보는 모든 화면에서 정적 마스킹으로 노출. 권한 분기는 백엔드에서 처리하며, 프론트의 토글·"전체 보기" 버튼은 제공하지 않음. |
| **감사 로그 자동 기록** | 모든 데이터 변경 액션(등록·수정·삭제·정지·환불 등)은 감사 로그에 자동 기록 (어드민 ID·시각·IP·변경 내용·사유) |
| **검색 컬럼 선택형** | 모든 메뉴의 검색은 [컬럼 드롭다운] + [단일 입력창] 조합으로 통일. placeholder는 선택된 컬럼에 따라 동적 변경. |
| **테이블 헤더 통일** | 모든 테이블 액션 컬럼명은 "처리"로 통일 ("액션" 사용 금지) |

## 1. 회원관리

### 1-1. 화면 IA

```
회원관리 페이지
├── [개인 회원 탭] (기본)
│   ├── Summary (4개 카드): 전체 / 정상 / 정지 / 탈퇴
│   ├── 검색 필터 (컬럼 선택형 4종)
│   │   └── 닉네임 / 회원번호 / 전화번호 / 이메일
│   ├── 회원 리스트 테이블 (10개 컬럼)
│   └── 페이지네이션
└── [셀러 회원 탭]
    ├── Summary (5개 카드): 전체 / 정상 / 정지 / 정산 보류 / 월 GMV
    ├── 검색 + 상태/정산/카테고리 필터
    └── 셀러 리스트 테이블 (9개 컬럼)
```

### 1-2. 정책

#### 1-2-1. 공통 조회 정책

| 정책 항목 | MVP 정의 |
|-----------|----------|
| **조회 단위** | 개인 회원 / 셀러 회원 분리 탭 |
| **조회 권한** | 모든 어드민 가능 |
| **수정 권한** | **기본 없음** - 정지/해제만 가능 (분쟁 등 특수 케이스) |
| **개인정보 노출** | **모든 화면에서 정적 마스킹** - 권한 분기는 백엔드에서 처리 |
| **회원 정보 직접 수정** | ❌ 불가 (회원이 직접 수정해야 함) |
| **회원 탈퇴 강제** | ❌ 불가 (회원이 직접 탈퇴 가능) |
| **회원 정지 (계정 잠금)** | ✅ 가능 (분쟁/사기 의심 등) |

| **셀러 상세** | 행 클릭 / [상세] | 사업자 정보 + 셀러 운영 정보 + 입점 이력 + 약관·마케팅 동의 + 활동 요약 |
| **결제수단** | 셀러 행 [결제수단] | PG 계약 요약 + 결제수단별 MID 리스트 + 정산 계좌 |

#### 1-2-6. 약관·마케팅 동의 표시 (모달 내)

**개인 회원 표시 항목 (8개)**:
| 약관 항목 | 구분 |
|-----------|------|
| 서비스 이용약관 | 필수 |
| 개인정보 처리방침 | 필수 |
| 마케팅 정보 수신 (전체) | 선택 |
| └ 알림톡 / 카카오 메시지 | 선택 |
| └ SMS / LMS | 선택 |
| └ 이메일 | 선택 |
| 야간 마케팅 수신 (21:00~08:00) | 선택 |
| 제3자 정보 제공 | 선택 |

**셀러 표시 항목 (8개)**: 셀러 이용약관 / 개인정보 처리방침 / 전자금융거래 약관 / 마케팅 정보 수신 (운영자→셀러) + 하위 3종 / 제3자 정보 제공

각 항목별 **최초 동의일 / 최근 변경일** 함께 노출. 어드민은 **조회만 가능**, 변경은 회원/셀러가 직접 수행.

### 1-3. 가능한 액션 정책

| 액션 | 권한 | 처리 방식 |
|------|------|----------|
| 회원 상세 조회 | OP / SVC | 모달 표시 |
| 주문 이력 조회 | OP / SVC | 주문관리로 이동 |
| 1:1 문의 이력 조회 | OP / SVC | 셀러별 문의 내용 확인 |
| 계정 정지 | SVC / OP는 승인 필요 | 사유 입력 + 정지 기간 설정 |
| 계정 정지 해제 | SVC | 사유 입력 |
| 셀러 콘솔 대리 접속 | SVC | 사유 입력 + 로그 (CS 지원 케이스) |

### 1-4. 정지 처리 정책 (셀러)

| 정책 항목 | 정의 |
|-----------|------|
| **정지 사유 코드** | `SETTLEMENT_OVERDUE`(정산 미납) / `POLICY_VIOLATION`(정책 위반) / `FRAUD_SUSPECT`(사기 의심) / `BUYER_DISPUTE`(구매자 분쟁) / `OTHER`(기타) |
| **정지 시 영향** | 콘솔 접근 차단 · 송출앱 로그인 차단 · 매니저 접근 차단 · 등록 상품 자동 비노출 · MID 자동 비활성화 · 진행 중 주문은 정상 처리(어드민 대리 처리 가능) · 정산 청구 유지 |
| **정지 알림** | 셀러에게 알림톡 + 이메일 자동 발송 |
| **해제 권한** | SVC만 |
| **해제 시 복구** | 콘솔 접근 회복 · 비노출된 상품 복구 · MID 활성화 (자동) |

### 1-5. Edge Case

| 케이스 | 처리 방안 |
|--------|-----------|
| 동명이인 검색 결과 다수 | 가입일·휴대폰번호로 정렬, 다중 결과 명시 |
| 탈퇴 회원 조회 | 5년간 익명화 보존 데이터 확인 가능 (법적 보존 기간) |
| 셀러 정지 시 진행 중 방송 | 자동 종료 + 정지 알림 발송 |
| 셀러 정지 시 미배송 주문 | 셀러는 콘솔 접근 불가, 어드민이 대리 처리 가능 (송장 입력 등) |
| 회원 정지 시 결제 진행 중 | 정지는 즉시 적용, 진행 중 결제는 정상 처리 |
| 동일 카카오 회원의 다른 채널 가입 | 채널별 user_id 별도 발급 (격리 멤버 풀 정책) |
| 셀러 가입 + 개인 회원 동시 보유 | 1 카카오 회원이 셀러+개인 둘 다 가능 (별도 플래그) |

## 2. 승인관리

### 2-1. 화면 IA

```
승인관리 페이지
├── 상태 흐름 stepper (신청 접수 → 수기 검토 → 승인 / 반려 / 보류)
├── Summary (5개 카드)
│   └── 승인 대기 / 승인 / 보류 / 검토 경과 / 반려
├── 공통 검색 필터 (컬럼 선택형 6종)
├── 5개 탭
│   ├── 전체 (기본)
│   ├── 승인 대기
│   ├── 승인
│   ├── 보류
│   └── 반려
└── 탭별 리스트 테이블
    ├── 공통 12개 컬럼 (모든 탭 동일)
    ├── 보류 탭: + 보완 요청 사유 (맨 뒤)
    └── 반려 탭: + 반려 사유 (맨 뒤)
```

### 2-2. 정책

#### 2-2-1. 승인 정책

| 정책 항목 | MVP 정의 |
|-----------|----------|
| **승인 방식** | **수기 승인** (자동 검증 미사용 — 사업 초반 정책) |
| **SLA** | 영업일 기준 **3일 이내** |
| **신청 상태** | 승인 대기 / 보류 (보완요청) / 승인 / 반려 / 검토 경과 (SLA 초과) |
| **재신청 정책** | **무조건 재신청 허용** (MVP) — 횟수 제한 없음 |
| **재신청 차단** | ❌ 미제공 (정책 위반은 셀러 정지로 별도 처리) |
| **승인 결과 알림** | 이메일 + 알림톡 발송 |
| **승인 취소** | 승인 후 정책 위반 적발 시 어드민이 셀러 정지 처리 (회원관리 메뉴) |

#### 2-2-2. 검색 정책

| 검색 컬럼 | placeholder |
|----------|-------------|
| 상호명 (기본) | 상호명을 입력하세요 |
| 회원번호 | 회원번호 (예: 12345678) |
| 사업자번호 | 사업자번호 (예: 123-45-67890) |
| 전화번호 | 전화번호 (예: 010-1234-5678) |
| 대표자명 | 대표자명을 입력하세요 |
| 담당자명 | 담당자명을 입력하세요 |

검색은 페이지 상단 1곳에 통합 (탭마다 별도 검색창 두지 않음).

#### 2-2-3. 공통 컬럼 (모든 탭 동일, 12개)

| 순서 | 컬럼명 | 마스킹 | 비고 |
|----|--------|------|------|
| 1 | 회원번호 | ✅ | `12345****` |
| 2 | 상호명 | - | - |
| 3 | 사업자번호 | - | `678-90-12345` (전체 노출) |
| 4 | 카테고리 | - | 푸드/식품, 패션/의류 등 |
| 5 | 전화번호 | ✅ | `010-****-1234` |
| 6 | 대표자명 | ✅ | `박**` |
| 7 | 담당자명 | ✅ | `김**` |
| 8 | 신청일시 | - | YYYY-MM-DD HH:MM |
| 9 | 상태 | - | 승인 대기 / 보류 / 승인 / 반려 / 검토 경과 |
| 10 | 경과 | - | "{N}일", SLA 초과 시 빨간색 강조 |
| 11 | 처리자 | - | "조클루니 (나)" / "김운영" / "미배정" |
| 12 | 처리 | - | [검토 시작] / [상세] |

**탭별 추가 컬럼**:
- 승인 탭: 경과 → **승인일**로 의미 변경
- 반려 탭: 경과 → **반려일**로 의미 변경, 맨 뒤에 **반려 사유** 컬럼 추가
- 보류 탭: 맨 뒤에 **보완 요청 사유** 컬럼 추가

### 2-3. 검토 처리 플로우

```
1. 승인 대기 탭에서 신청 건 클릭 또는 [검토 시작] 클릭
2. 신청 상세 모달 오픈
   - 사업자 정보 (사업자번호 / 통신판매업 / 상호 / 대표자 / 연락처 / 카테고리 / 거래액 / 방송 횟수 / 판매 구조)
   - 제출 서류 (사업자등록증·통신판매업 등록증 PDF 미리보기)
   - 검토 메모 (내부용 텍스트에어리어)
3. 4가지 처리 액션 중 선택:
   a) [승인] → 토스트 + 모달 닫힘 + 셀러에게 승인 알림
   b) [검토 보류] → 보류 사유 입력 모달 오픈
   c) [추가 서류 요청] → 보류 상태 전환 + 셀러에게 추가 서류 요청 알림
   d) [반려] → 반려 사유 입력 모달 오픈
```

### 2-4. 보류 사유 모달 정책

| 필드 | 형태 | 옵션 |
|------|------|------|
| **보완 요청 항목** | 드롭다운 (필수) | 사업자등록증 재제출 / 통신판매업 등록증 재제출 / 통신판매업 만료 임박 / 정산 계좌 예금주 정정 / 대표자 본인 인증 정보 불일치 / 카테고리 정보 추가 확인 / 담당자 연락처/이메일 확인 / 기타 |
| **셀러에게 전달 메시지** | 텍스트에어리어 (필수) | 알림톡 + 콘솔에 그대로 노출 |
| **처리자 메모** | 텍스트에어리어 | 내부용 (셀러 비노출) |

처리 액션: `[보류 처리 + 알림 발송]` → 상태 보류 전환 + 셀러 알림톡 자동 발송.

### 2-5. 반려 사유 모달 정책

| 필드 | 형태 | 비고 |
|------|------|------|
| **반려 사유 코드** | 드롭다운 (필수) | 9개 코드 (아래 참조) |
| **셀러에게 전달 메시지** | 텍스트에어리어 (필수) | 알림톡 + 콘솔에 그대로 노출 |
| **처리자 메모** | 텍스트에어리어 | 내부용 |

#### 반려 사유 코드 (9개)

| 코드 | 설명 |
|------|------|
| `BIZ_NUM_INVALID` | 사업자번호 무효 (국세청 조회 실패 또는 폐업) |
| `BIZ_NUM_MISMATCH` | 사업자 정보 불일치 |
| `LICENSE_MISSING` | 통신판매업 등록증 누락 |
| `LICENSE_INVALID` | 통신판매업 등록증 무효 (만료 또는 잘못된 정보) |
| `ACCOUNT_VERIFY_FAIL` | 정산 계좌 실명 확인 실패 |
| `CATEGORY_NOT_ALLOWED` | 취급 불가 카테고리 (무형상품 등) |
| `DUPLICATE_APPLY` | 중복 신청 (동일 사업자번호 기존 가입) |
| `INSUFFICIENT_INFO` | 정보 부족 (필수 항목 누락) |
| `OTHER` | 기타 (직접 입력) |

처리 액션: `[반려 처리 + 알림 발송]` → 상태 반려 전환 + 셀러 알림 발송. **반려된 셀러는 정정 후 재신청 가능** (MVP는 횟수 제한 없음).

### 2-6. Edge Case

| 케이스 | 처리 방안 |
|--------|-----------|
| 영업일 3일 초과 미처리 | 상단 카드 "검토 경과 (SLA 초과)" 카운트 + 행 빨간색 강조 |
| 동일 사업자번호 재신청 | 변경 사항 없이 재신청 시 시스템 자동 차단 |
| 검토 중 신청자가 신청 취소 | 신청 취소 가능 (검토 큐에서 제거) |
| 추가 서류 요청 후 미회신 (7일 경과) | 자동 보류 + 셀러 알림 |
| 동일 대표자명의 다른 사업자로 재가입 | 신규 신청으로 처리 (별도 검토) |
| 보류 처리 중 셀러가 정정 후 재제출 | 자동으로 [승인 대기] 탭으로 이동 |
| 반려 후 셀러가 동일 정보로 재신청 | 시스템에서 동일성 체크, 변경 사항 없으면 차단 |

## 3. 셀러별 결제수단 관리

> ⭐ **핵심 메뉴** - PG 연동 라우팅의 기준이 되는 메뉴 (SVC 전용)

### 3-1. 화면 IA

```
결제수단 관리 페이지 (SVC ONLY)
├── 페이지 헤더 (+ MVP 정책 명시)
│   "MVP는 토스페이먼츠 단일 PG (신용카드 / 실시간 계좌이체)"
├── [+ MID 등록] 버튼 → 등록 모달 (모드: register)
├── 결제 라우팅 흐름 시각화 (5단계, 다크 그라데이션)
│   "User → Grip 시스템 → MID 매핑 조회 → PG → 셀러 직접 정산"
├── Summary (5개 카드): 활성 셀러 / 등록 MID / 활성 / 검증실패 / 비활성
├── 필터 (셀러 / 결제수단 / 상태)
└── MID 리스트 테이블 (8개 컬럼)
    └── 행별 [수정] 버튼 → 수정 모달 (모드: edit, 셀러 락)
```

### 3-2. 정책

#### 3-2-1. 결제수단 정책 (MVP)

| 정책 항목 | MVP 정의 |
|-----------|----------|
| **PG사** | **토스페이먼츠 단일** (UI는 disabled로 고정 표시) |
| **결제수단** | **신용카드 / 계좌이체 (실시간)** 2종만 |
| **PG 계약 주체** | **셀러가 직접** PG사와 계약 (Grip은 중개 X) |
| **MID 발급 주체** | 셀러가 PG로부터 발급받아 Grip에 전달 |
| **MID 등록 주체** | **SVC만 가능** (보안상) |
| **결제수단별 MID** | 결제수단마다 별도 MID 가능 (예: 신용카드용·계좌이체용) |
| **MID 검증** | PG사 API로 등록 즉시 유효성 검증 (성공: 활성 / 실패: 검증실패) |
| **결제 라우팅** | User 결제 시 → 셀러 ID + 결제수단 → MID 매핑 → PG 전달 |
| **셀러 정산** | PG → 셀러 직접 (Grip 미관여) |

> **확장 계획 (v1+)**: 가상계좌·간편결제(토스페이/네이버페이/카카오페이)·다른 PG(KCP·NICE 등) 추가 시점에 등록 폼 옵션 확장.

#### 3-2-2. 결제 라우팅 흐름

```
[1. User]                    [2. Grip 시스템]              [3. 본 메뉴 ⭐]            [4. PG]                [5. 셀러]
결제수단 선택       →        셀러 ID + 결제수단 추출   →   MID 매핑 조회       →    결제 처리       →    직접 정산
                                                          (seller_payment_methods)                          (Grip 미관여)
```

매핑 결과 처리:
- **활성 MID 존재** → PG로 요청 전달 (해당 MID 포함)
- **매핑 없음** → "셀러가 해당 결제수단을 지원하지 않아요" 에러
- **비활성 / 검증실패** → "일시적으로 사용할 수 없어요" 에러 + 다른 결제수단 안내

### 3-3. 리스트 화면

#### 3-3-1. 필터

| 필터 | 옵션 |
|------|------|
| 셀러 | 텍스트 입력 (상호명 / 채널명) |
| 결제수단 | 전체 / 신용카드 / 계좌이체 (실시간) |
| 상태 | 전체 / 활성 / 비활성 / 검증실패 |

> **PG사 필터 미제공**: MVP는 토스페이먼츠 단일이므로 의미 없어 제거.

#### 3-3-2. 리스트 컬럼 (8개)

| 순서 | 컬럼명 | 마스킹 | 비고 |
|----|--------|------|------|
| 1 | 셀러 (채널) | - | "SLR-001 · 차차언니" |
| 2 | 결제수단 | - | 신용카드 / 계좌이체 (실시간) |
| 3 | PG사 | - | 토스페이먼츠 |
| 4 | MID (가맹점 ID) | ✅ | `T0***1234` + 암호화 태그 |
| 5 | 등록일 | - | YYYY-MM-DD |
| 6 | 등록자 | - | 어드민 ID |
| 7 | 상태 | - | 활성 / 비활성 / 검증실패 |
| 8 | 처리 | - | [수정] / [비활성화] / (검증실패 시) [검증 재시도] / (비활성 시) [활성화] |

### 3-4. MID 등록 모달 (등록 모드)

#### 3-4-1. 입력 필드

| 필드 | 필수 | 형태 | 설명 |
|------|------|------|------|
| **셀러 선택** | ✅ | **검색 콤보박스** | 셀러 ID / 상호명 / 채널명으로 실시간 필터링 |
| **결제수단** | ✅ | 드롭다운 | 신용카드 / 계좌이체 (실시간) |
| **PG사** | - | 고정 (disabled) | 토스페이먼츠 (변경 불가) |
| **MID (가맹점 ID)** | ✅ | 텍스트 | PG사가 셀러에게 발급한 ID |
| **MID 시크릿 키** | ✅ | password | KMS 암호화 저장. 다시 조회 불가 |
| 사이트 코드 / 가맹점명 | - | 텍스트 | PG사별 추가 식별 정보 |
| 활성 여부 | ✅ | 드롭다운 | 활성 (기본) / 비활성 |
| 비고 (어드민 메모) | - | 텍스트에어리어 | 셀러 협의 일정·PG 계약 만료일 등 |

#### 3-4-2. 셀러 검색 동작

| 동작 | 처리 |
|------|------|
| 입력칸 포커스 | 옵션 리스트 펼침 |
| 키보드 입력 (`oninput`) | 실시간 필터링 (셀러 ID / 상호명 / 채널명 모두 매칭) |
| 옵션 클릭 | 입력칸에 "SLR-XXX · 채널명 (상호명)" 채움 + 리스트 닫힘 |
| 검색 결과 0건 | "검색 결과가 없습니다" 안내 |
| 외부 클릭 | 옵션 리스트 자동 닫힘 |

#### 3-4-3. 처리 액션

`[등록 + 검증]` → 모달 닫힘 + 토스트: "✅ MID 등록 완료. PG 검증 진행 중 (1~3초)..."

### 3-5. MID 수정 모달 (수정 모드)

기존 등록 모달과 **같은 모달을 모드 분기**로 재사용 (`openMidModal('edit', data)`).

#### 3-5-1. 등록 모드와 차이점

| 영역 | 등록 모드 | 수정 모드 |
|------|----------|----------|
| 모달 타이틀 | "💳 결제수단 / MID 등록" | "✏️ 결제수단 / MID 수정" |
| **셀러 선택** | 🔍 검색 콤보박스 | 🔒 **읽기 전용** (회색 박스) |
| **MID 시크릿 키** | 필수 (`*`) | 선택 (변경 시에만 입력, 비우면 기존 값 유지) |
| 시크릿 키 헬프 | 빨간색 경고: "다시 조회 불가" | 회색 안내: "변경할 때만 입력" |
| 제출 버튼 | "등록 + 검증" | "수정 + 재검증" |

#### 3-5-2. 셀러 변경 불가 정책

수정 시 셀러는 변경할 수 없음. 셀러를 변경해야 하는 경우:
1. 기존 등록을 [비활성화]로 처리
2. 새 셀러로 [+ MID 등록] 신규 등록

> **이유**: MID는 셀러-PG 계약의 1:1 매핑 키. 셀러 교체 시 결제 라우팅 무결성 깨짐 + 감사 로그 추적 어려움.

### 3-6. 보안 정책

| 항목 | 정책 |
|------|------|
| **MID 시크릿 저장** | DB에 KMS 암호화 저장 |
| **노출** | 어드민 화면에서도 마스킹 표시 (`T0***1234`), 추가 인증 후에도 평문 미노출 (재발급만 가능) |
| **변경 이력** | 모든 등록·수정·삭제 액션 감사 로그 (어드민 ID·시각·IP·변경 내용) |
| **권한** | SVC만 등록·수정 가능 / OP는 조회만 (마스킹) |
| **검증** | 등록 시 PG API로 MID 유효성 자동 검증 |

### 3-7. Edge Case

| 케이스 | 처리 방안 |
|--------|-----------|
| MID 등록 후 PG 검증 실패 | "검증실패" 상태로 등록 (User 결제 불가), 셀러에게 정정 요청 |
| 동일 셀러·결제수단 중복 등록 시도 | 기존 등록 비활성화 후 신규 등록 (정책 결정 후 차단 가능) |
| 셀러가 PG 계약 해지 (Grip 미통보) | 결제 시 PG에서 거부 → "결제 일시 불가" 에러, 어드민 알림 |
| MID 시크릿 키 노출 사고 | 즉시 비활성화 + 셀러에게 신규 발급 요청 |
| 셀러 정지 시 결제수단 처리 | 자동 비활성화, 셀러 활성화 시 자동 복구 |
| User가 셀러 미등록 결제수단 선택 시도 | User 결제 화면에서 자동 필터링 (UI 차단) |
| 결제 진행 중 MID 비활성화 | 트랜잭션 보호 (시작된 결제는 완료까지 진행) |
| PG 측 점검 시간 결제 | "PG 점검 중입니다. 잠시 후 다시 시도해주세요" 에러 |
| 다수 결제수단 동시 등록 (엑셀 일괄 업로드) | 각 행별 검증, 실패 행은 결과 리포트 표시 (v1+) |
| 수정 모드에서 시크릿 키 비워둠 | 기존 값 유지 (변경 안 함) |
| 수정 모드에서 시크릿 키 새로 입력 | 신규 키로 교체 + PG 재검증 |

## 4. 주문관리

### 4-1. 화면 IA

```
주문관리 페이지
├── Summary (4개 카드): 오늘 주문 / 오늘 결제액 / 결제대기 / 취소·환불
├── 검색 필터 (컬럼 선택형 7종 + 주문날짜 + 상태 + 결제수단)
└── 주문 카드 리스트 (펼침형)
    └── 주문 카드 (4개 영역)
        ├── 헤더 (클릭 시 토글)
        │   └── 주문번호 + 셀러 + 주문자 + 상태 / 금액 + 결제수단
        └── 본문 (펼침 시)
            ├── 상품주문 정보 (PO 그룹핑)
            ├── 정보 3분할 (결제 / 배송 / 주문자)
            └── 상태 변경 이력 (시간순)
```

### 4-2. 정책

#### 4-2-1. 핵심 정책

| 정책 항목 | MVP 정의 |
|-----------|----------|
| **조회 권한** | 모든 어드민 조회 가능 |
| **수정 권한** | **기본 없음** - 분쟁 개입 시에만 (SVC) |
| **상세 표시 방식** | **모달 미사용** - 카드 펼침으로 인라인 노출 |
| **주문 표시 단위** | 주문번호 (ORD-) 단위 카드 + 하위 상품주문번호 (PO-) 그룹핑 |
| **개인정보 마스킹** | 배송지·연락처 모두 마스킹 (권한별 차등은 백엔드 처리) |

### 4-3. 주문 카드 구조

#### 4-3-1. 헤더 (항상 표시, 클릭 시 토글)

```
[주문번호 영역]            [요약 정보]                        [금액 영역]            [▾]
ORD-2026-04223              차차언니 · 그립조아 (12345****)    59,800원
                            2026-04-22 15:42 · [배송중]        신용카드 · 토스페이먼츠
```

| 영역 | 내용 |
|------|------|
| 주문번호 | `ORD-YYYY-NNNNN` 모노스페이스 |
| 메인 정보 | 셀러명 + 주문자 닉네임 + 회원번호(마스킹) + 주문일시 + 상태 배지 |
| 금액 | 총 결제 금액 (큰 폰트) + 결제수단·PG사 (작은 회색) |
| 토글 | `▾` 아이콘 (펼침 시 회전) |

기본 상태: 전체 접힘. 페이지 진입 시 첫 카드만 펼친 상태로 시작 (UX 가이드).

#### 4-3-2. 본문 (펼침 시 표시)

##### A. 상품주문 정보 (PO 그룹핑)

```
📦 상품주문 정보 (N건)
┌────────────────────────────────────────────────────────────┐
│ PO-04223-01  봄 데님 자켓                  39,800원  [배송중]   │
│              옵션: 블루, M · 수량 1개                          │
├────────────────────────────────────────────────────────────┤
│ PO-04223-02  리넨 셔츠                     17,000원  [배송중]   │
│              옵션: 화이트, S · 수량 1개                         │
└────────────────────────────────────────────────────────────┘
상품 합계 56,800원 + 배송비 3,000원 = 59,800원
```

각 PO 행 구조 (4컬럼 그리드):
| 영역 | 내용 |
|------|------|
| PO 번호 | `PO-NNNNN-NN` (인디고색) |
| 상품 정보 | 상품명 (굵게) + 옵션·수량 (회색) |
| 금액 | 우측 정렬 |
| 상태 | 우측 정렬 배지 |

부분 발송 시 각 PO별 상태가 다를 수 있음 (예: PO-01은 배송완료, PO-02는 배송중).

##### B. 정보 3분할

| 영역 | 항목 (마스킹 적용) |
|------|------------------|
| **💳 결제 정보** | 결제수단 / PG사 / 사용 MID / 승인번호 / 승인시각 / 결제 금액 / (취소 시) 환불 금액 / 환불 시각 |
| **🚚 배송 정보** | 배송지 / 상세주소 / 수령인 / 연락처 / 배송메모 / 택배사 / 송장번호 |
| **👤 주문자 정보** | 회원번호 / 닉네임 / 전화번호 / 이메일 / 셀러 / 주문일시 |

##### C. 상태 변경 이력 (시간순 테이블)

| 컬럼 | 내용 |
|------|------|
| 일시 | YYYY-MM-DD HH:MM |
| 상태 | 결제대기 / 결제완료 / 배송준비중 / 배송중 / 배송완료 / 취소 / 환불완료 (배지) |
| 처리 주체 | 시스템 (PG 콜백) / 시스템 (택배 API) / 셀러 (Owner/Staff) / 구매자 / 어드민 |

### 4-5. Edge Case

| 케이스 | 처리 방안 |
|--------|-----------|
| 다품목 주문 부분 발송 | PO별 상태 개별 표시 (예: PO-01 배송완료, PO-02 배송중) |
| 부분 취소 | 해당 PO만 취소 상태, 나머지는 유지 |
| 결제대기 24시간 초과 | 시스템 자동 취소 + 상태 이력에 "시스템 자동 취소" 기록 |
| 환불 발생 주문 | 결제 정보 영역에 환불 금액·시각 추가 표시 |
| 송장번호 오입력 (셀러) | 택배 API 조회 실패 → 상태 이력에 "조회 실패" 기록 |
| 진행 중 환불 | 상태 이력에 진행 단계 기록 (요청 → 셀러 환불 처리 → 환불 완료) |
| 어드민이 강제 환불·취소 필요 | **본 메뉴에서 미지원** → 1:1 문의·CS 채널로 처리 |
| 다른 셀러 채널의 동일 회원 주문 | 채널별 user_id 별도이므로 회원번호로 검색해도 채널별 분리 표시 |
